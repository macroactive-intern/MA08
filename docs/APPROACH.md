Goal

I am building a Laravel JSON API for tracking client progress over time.

The API has two main parts:

Measurements
Clients can create, list, update, and delete their own body measurements.
A client can only have one measurement for each calendar day.
Measurements can be filtered by date range.
Progress photos
Clients can upload progress photos.
The uploaded file is stored on the local disk.
The database stores photo metadata only.
Clients can list their own photo metadata.
Clients can delete a photo, which deletes both the database row and the file from disk.

Coaches can use coach-only endpoints to view a client’s measurement history and photo metadata.

All routes will require Sanctum authentication.

I will write the feature tests first, then build the implementation until the tests pass.

measurements

The measurements table stores body measurement records for users.

Column	Type	Notes
id	bigIncrements	Primary key
user_id	foreignId	References users.id
measured_at	date	Calendar date of the measurement
weight	decimal(5,2)	Nullable
body_fat_percentage	decimal(4,1)	Nullable
notes	text	Nullable
unit_system	enum	metric or imperial
created_at	timestamp	Laravel timestamp
updated_at	timestamp	Laravel timestamp

The migration will include:

$table->foreignId('user_id')->constrained()->cascadeOnDelete();
$table->date('measured_at');
$table->decimal('weight', 5, 2)->nullable();
$table->decimal('body_fat_percentage', 4, 1)->nullable();
$table->text('notes')->nullable();
$table->enum('unit_system', ['metric', 'imperial']);
$table->timestamps();

$table->unique(['user_id', 'measured_at']);
One measurement per day constraint

The exact database constraint will be:

$table->unique(['user_id', 'measured_at']);

This means:

One user cannot have two measurements for the same calendar date.
Different users can have measurements on the same calendar date.
The rule is protected at database level, not only in controller validation.

Validation approach
Store measurement validation

Request: StoreMeasurementRequest

Rules:

[
    'measured_at' => ['required', 'date'],
    'weight' => ['nullable', 'numeric'],
    'body_fat_percentage' => ['nullable', 'numeric'],
    'notes' => ['nullable', 'string'],
    'unit_system' => ['required', Rule::in(['metric', 'imperial'])],
]

The duplicate date rule will be checked for the authenticated user.

The validation should return 422 if the same user already has a measurement with the same measured_at date.

Update measurement validation

Request: UpdateMeasurementRequest

Rules will be similar to store validation.

The update must allow the current measurement to keep its own date, but it must block changing the date to another date already used by the same user.

Example:

Existing measurement 1: 2026-06-15
Existing measurement 2: 2026-06-16
User tries to update measurement 2 to 2026-06-15
API returns 422
Store photo validation

Request: StoreProgressPhotoRequest

Rules:

[
    'photo' => [
        'required',
        'file',
        'mimetypes:image/jpeg,image/png,image/webp',
        'max:5120',
    ],
    'taken_at' => ['required', 'date'],
    'caption' => ['nullable', 'string', 'max:200'],
]

The maximum size is 5120 KB, which is 5 MB.

MIME validation decision

The acceptance criteria say file format validation must be based on MIME type, not file extension.

I will use:

mimetypes:image/jpeg,image/png,image/webp

This checks the detected MIME type of the uploaded file.

This matters because file extensions can be faked. For example, a file called photo.jpg might not actually be a JPEG image.

Image format decision

The brief says the app accepts “any common image format,” but the acceptance criteria say only JPEG, PNG, and WEBP are accepted.

I will implement the acceptance criteria because they are more specific and testable.

Accepted:

JPEG
PNG
WEBP

Rejected:

GIF
HEIC
BMP
TIFF
PDF
Any non-image file

Rejected formats will return 422.

Unit storage decision

The API will store measurements as provided.

There will be no unit conversion.

If a client submits:

{
  "weight": 185,
  "unit_system": "imperial"
}

The database stores:

weight = 185
unit_system = imperial

It does not convert 185 lbs into kilograms.

This means coaches must check the unit_system before comparing measurements between clients. A metric value and an imperial value cannot be safely compared as the same unit.

File storage approach

Uploaded progress photos will be stored on the local disk.

The app will store files under:

storage/app/progress-photos/

The database will store the relative path, for example:

progress-photos/0f4757d7-dc20-4df6-9f36-f4b4c9aaf7b1.webp

The implementation will use Laravel’s local disk:

Storage::disk('local')
Filename strategy

The client’s original filename will not be used in the stored path.

Instead, I will generate a UUID filename.

Example:

$filename = (string) Str::uuid() . '.webp';
$path = 'progress-photos/' . $filename;

The extension will be chosen from the validated MIME type.

Example mapping:

image/jpeg => jpg
image/png => png
image/webp => webp

This avoids:

Filename collisions.
Unsafe characters in filenames.
Path manipulation risks.
Accidentally exposing private information from original filenames.
Photo delete approach

When DELETE /api/photos/{id} is called:

Find the photo record.
Check that the authenticated user owns the photo.
If the user does not own it, return 403.
Delete the file from the local disk using the saved storage_path.
Delete the database record.
Return a success response.

After the request completes:

The file should no longer exist on disk.
The database row should no longer exist.
A direct filesystem check should show there is no orphaned file.

The test will assert both:

Storage::disk('local')->assertMissing($photo->storage_path);
$this->assertDatabaseMissing('progress_photos', ['id' => $photo->id]);

Authorization approach
Normal client routes

Clients can only access their own records.

For list endpoints, I will scope by authenticated user:

where('user_id', auth()->id())

For update/delete endpoints, I will compare the record owner to the authenticated user:

if ($measurement->user_id !== auth()->id()) {
    abort(403);
}

The same approach applies to progress photos.

Coach routes

Coach endpoints require:

auth()->user()->role === 'coach'

If the authenticated user is not a coach, return 403.

The brief says coaches can view their clients’ progress history, but it does not define a coach-client relationship table.

Because the relationship is not specified, I will not invent one. For this implementation, any authenticated user with role = coach can access the requested client’s progress records.

Edge cases
Duplicate measurement dates

A user cannot have two measurements with the same measured_at date.

This is handled by both:

Form request validation.
Database unique constraint.

The database constraint protects the app if two duplicate requests happen close together.

Updating into a duplicate date

The duplicate date rule also applies on update.

The update validation must ignore the current measurement but still block dates already used by the same user.

Different users using the same date

Different users can have measurements on the same date.

The unique constraint is on:

user_id + measured_at

not only measured_at.

Invalid unit system

Only these values are accepted:

metric
imperial

Anything else returns 422.

No unit conversion

Measurements are stored exactly as submitted.

The system does not convert pounds to kilograms or kilograms to pounds.

Invalid photo format

Only JPEG, PNG, and WEBP are accepted.

Other files return 422.

This includes:

GIF
HEIC
BMP
TIFF
PDF
Text files
Files with fake extensions
Oversized photo

Any upload larger than 5 MB returns 422.

Laravel validation will use:

max:5120
Original filename is unsafe

The original filename will not be used in the storage path.

The app will generate a UUID filename instead.

This avoids security and reliability issues.

Deleting another user’s photo

The app must check ownership before deleting a file.

If the user does not own the photo:

Return 403.
Do not delete the file.
Do not delete the database row.
File missing during delete

If the database record exists but the file is already missing from disk, the app should still delete the database row.

The desired final state is:

No database row.
No file on disk.

This avoids keeping broken metadata forever.

Photo list should not return binary data

GET /api/photos returns metadata only.

It should not read the file content from disk and should not return binary image data.

Date filters

GET /api/measurements supports:

start_date
end_date

Behavior:

start_date returns measurements on or after that date.
end_date returns measurements on or before that date.
Both together return measurements inside the inclusive range.
Future dates

The brief does not say future dates are invalid.

I will validate measured_at and taken_at as dates, but I will not block future dates unless tests or later instructions require it.
